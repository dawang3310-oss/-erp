# Windows 生产主机完整迁移设计

## 1. 背景与约束

本设计用于把电商 ERP 从一台 Windows＋Docker Desktop 主机完整迁移到另一台 Windows＋Docker Desktop 主机。迁移范围包含：

- Git、源代码、设计文档、生成素材和未跟踪资料；
- MySQL 业务数据库；
- MinIO 对象；
- Redis 缓存与短期协调状态；
- RocketMQ Topic、消费组、ACL 和待处理任务；
- Docker Compose、镜像、卷信息和网络配置；
- 应用配置、环境变量、平台凭证、证书和密钥；
- Windows 计划任务、服务、防火墙、反向代理和启动配置；
- 域名、DNS、固定 IP、平台回调及白名单；
- 监控、日志、告警、备份和恢复资料。

业务允许停机 2–4 小时。当前总数据量未知，因此正式迁移前必须执行只读盘点。迁移选择分层逻辑迁移，不使用 Docker Desktop WSL/VHDX 复制或整机克隆作为主要恢复方式。

## 2. 核心决策

### 2.1 主要恢复源

- MySQL 使用一致性逻辑备份；数据量较大时使用 MySQL Shell 并行导出。
- MinIO 使用对象级镜像和校验。
- Redis 不迁移旧缓存、会话、锁或短期协调数据，新主机从空实例启动。
- RocketMQ 在切换前停止生产者并排空积压，在新主机重建配置。
- Git 使用仓库 bundle、普通远端和独立未跟踪文件归档共同保护。
- Docker 镜像优先按固定摘要重新拉取，本地或私有镜像使用镜像归档。
- 密钥通过独立加密介质或密钥系统迁移，不进入 Git 或普通备份包。

### 2.2 保险副本

旧主机完全停止 Docker Desktop 后，可以额外备份 WSL/VHDX 数据盘。该副本只用于灾难取证和最后保险，不能替代 MySQL、MinIO、Git 和配置的可验证备份。

### 2.3 单主原则

任何时刻只能有一台主机执行生产写入。旧主机和新主机不得同时运行：

- 平台订单和售后拉取；
- 消息回调处理；
- 库存同步；
- 电子面单申请或取消；
- 发货和物流回传；
- 售后状态或退款回写；
- 产生生产 Outbox 的定时任务。

## 3. 迁移阶段

迁移分为五个阶段：

1. 只读盘点；
2. 新主机预搭建；
3. 预备份、预复制和恢复演练；
4. 2–4 小时停机切换；
5. 72 小时观察与旧主机保留。

每个阶段都有明确完成标准。前一阶段未通过，不能进入后一阶段。

## 4. 只读盘点

### 4.1 主机与运行时

记录：

- Windows 版本与补丁；
- Docker Desktop 和 WSL 版本；
- CPU、内存、磁盘、剩余空间和磁盘类型；
- 时区、NTP、主机名和网络接口；
- Java、Maven、Node.js、pnpm、Git 和 PowerShell 版本；
- Docker Engine、Compose 和镜像架构。

### 4.2 Docker

记录全部：

- Compose 项目；
- 容器及其镜像摘要；
- Docker 卷；
- 网络；
- 端口映射；
- 环境变量来源；
- 健康检查；
- 重启策略；
- 日志驱动；
- 卷挂载路径。

盘点表只记录敏感配置的名称和来源，不记录真实值。

### 4.3 数据规模

至少统计：

- MySQL 每个数据库、表、索引和总容量；
- MySQL 最大表及预计导出时间；
- MinIO Bucket、对象数量、总容量和最大对象；
- Redis RDB/AOF 大小、键数量和过期键比例；
- RocketMQ Topic、消费组、积压量和最老消息年龄；
- 每个 Docker 卷的容量；
- Git 仓库、工作树、未跟踪文件和大文件容量；
- 应用日志、审计日志和历史备份容量。

根据盘点结果选择传输介质：

- 总量较小且网络稳定：受控局域网加密传输；
- 总量较大或网络不稳定：加密移动 SSD；
- MySQL 较大：MySQL Shell 并行导出；
- MinIO 较大：提前预复制，停机窗口只做最终差异同步。

### 4.4 外部配置

记录：

- 域名和 DNS；
- 公网 IP 和 NAT；
- 平台回调地址和 IP 白名单；
- TLS 证书、到期时间和私钥位置；
- Windows 防火墙；
- Windows 服务和计划任务；
- 反向代理；
- 监控采集端；
- 告警接收人；
- 许可证或机器绑定配置。

### 4.5 业务基线

切换前准备只读基线查询，统计：

- 各平台订单总数和最近订单；
- 各状态订单数量；
- SKU 数量和未映射数量；
- 各仓库库存、预占和可售汇总；
- 履约、发货和异常单数量；
- 售后和退款数量及金额；
- Outbox 各状态数量；
- RocketMQ 积压；
- MinIO 业务对象数量。

这些汇总在正式停机后再记录最终值，并用于迁移后对账。

## 5. 新主机准备

新主机必须：

- 使用与旧主机兼容的 Windows、Docker Desktop 和 WSL 版本；
- 至少有有效数据量两倍的可用空间；
- 校准时区和时间同步；
- 配置独立的生产数据目录；
- 安装所需运行时；
- 配置防火墙、证书和反向代理；
- 接入监控和告警；
- 在隔离网络或临时端口启动；
- 默认关闭全部平台连接器和外部副作用任务。

新主机预搭建期间不能使用正式生产回调地址，不能执行库存、面单、发货或售后回写。

## 6. 备份设计

### 6.1 Git、代码和文档

每个仓库保存：

- 完整 Git bundle；
- 远端地址；
- 分支和标签清单；
- 当前 HEAD；
- 工作树清单；
- 未提交变更补丁；
- 未跟踪文件归档；
- LFS 或其他大文件；
- 设计稿、生成素材和运行文档。

不能只复制当前检出目录，因为这样可能遗漏未推送分支、标签和其他工作树。

### 6.2 MySQL

备份必须包含：

- 表结构和数据；
- 视图；
- 触发器；
- 存储过程和函数；
- Event Scheduler 事件；
- 字符集和排序规则；
- Flyway 历史表；
- 用户和权限的独立清单。

普通规模使用单事务一致性逻辑备份。数据量和恢复时间超过停机窗口时，改用 MySQL Shell 并行导出。正式恢复源不能是运行中复制的 Docker 卷。

备份后必须执行：

- 命令退出码检查；
- 文件大小检查；
- SHA-256；
- 在新主机测试恢复；
- 表数量、行数和业务基线对比。

### 6.3 MinIO

在业务运行时先执行预复制。正式停机后停止对象写入，再执行最终差异同步。

验证：

- Bucket 清单；
- 对象数量；
- 总容量；
- 版本和生命周期配置；
- 用户、策略和访问密钥；
- 抽样对象 SHA-256；
- ERP 附件和原始报文读取。

### 6.4 Redis

Redis 在本系统中只用于缓存和短期协调，因此：

- 不迁移分布式锁；
- 不迁移过期缓存；
- 不迁移临时会话和任务占用标志；
- 不把 RDB/AOF 作为生产恢复依赖；
- 新主机启动空 Redis，由应用重建缓存。

如果盘点发现 Redis 存在业务真相数据，必须先停止迁移并把该数据迁回 MySQL 或另行制定专用方案。

### 6.5 RocketMQ

正式切换前：

1. 停止消息生产者和产生 Outbox 的定时任务；
2. 让消费者继续工作；
3. 把业务积压降到零；
4. 导出 Topic、消费组、ACL、重试和死信配置；
5. 停止消费者；
6. 在新主机重建相同配置。

不得复制运行中的 Broker 存储目录。若积压无法在停机窗口内排空，必须延期迁移，或另行设计受控消息迁移和消费位点恢复。

### 6.6 Docker 镜像和 Compose

保存：

- Compose 文件；
- 环境变量模板；
- 镜像名称、固定标签和摘要；
- 自建镜像的构建来源；
- 私有仓库地址和访问方式。

可信镜像按摘要重新拉取。本地或无法重新获取的镜像使用镜像归档，并生成 SHA-256。

### 6.7 密钥和证书

单独迁移：

- MySQL 账户；
- MinIO 账户；
- RocketMQ ACL；
- JWT/JWK；
- 电商平台 `client_id/client_secret` 和 Token；
- TLS 证书和私钥；
- 备份加密密钥；
- 其他第三方凭证。

密钥包使用强加密和独立密码，通过离线介质或密钥系统交付。迁移完成并稳定后轮换关键密钥。

## 7. 传输与校验

每个迁移项都进入清单，包含：

- 唯一编号；
- 来源；
- 目标；
- 负责人；
- 备份时间；
- 大小；
- SHA-256；
- 恢复方式；
- 验证方式；
- 验证结果。

备份至少保留两份：

1. 旧主机本地只读副本；
2. 独立加密介质或受控备份位置。

新主机接收后必须先校验全部 SHA-256，再解压和恢复。校验不一致的备份不能使用。

## 8. 迁移前演练

正式切换前至少完成一次完整演练：

1. 使用最新备份恢复新主机；
2. 启动基础设施；
3. 启动 ERP，但保持连接器关闭；
4. 执行健康检查；
5. 登录并检查权限；
6. 查询订单、库存、售后和附件；
7. 执行业务基线对账；
8. 验证备份和恢复命令；
9. 记录完整耗时；
10. 确认可以在 2–4 小时内完成最终切换。

演练失败或耗时超出窗口时，必须调整备份方式、增加预复制或重新安排窗口。

## 9. 正式停机切换

### 9.1 切换前 7 天

- 完成完整恢复演练；
- 调低 DNS TTL；
- 申请新公网 IP、平台回调地址和白名单；
- 验证新主机磁盘、证书、监控和备份；
- 指定迁移负责人、业务验收人和回滚决定人；
- 发布停机通知。

### 9.2 旧主机停写

1. ERP 进入维护模式。
2. 禁止人工新增、修改和发货。
3. 关闭所有平台连接器和定时拉取。
4. 停止 RocketMQ 生产者。
5. 排空消息积压。
6. 记录最终业务基线。
7. 执行最终 MySQL 备份。
8. 执行 MinIO 最终差异同步。
9. 归档最终 Git、配置、审计和 SHA-256 清单。
10. 保持旧主机应用和连接器关闭。

旧主机容器、卷和备份不能在切换当天删除。

### 9.3 新主机恢复顺序

1. 恢复 MySQL。
2. 校验 Flyway、表、行数和关键业务汇总。
3. 恢复 MinIO。
4. 校验 Bucket、对象数量、容量和抽样文件。
5. 重建 RocketMQ 配置并确认无历史积压。
6. 启动空 Redis。
7. 启动 ERP 后端，保持连接器总开关关闭。
8. 启动前端、监控、日志和告警。
9. 执行只读健康检查和业务查询。
10. 对照旧主机最终业务基线。
11. 修改 DNS、反向代理、端口和平台白名单。
12. 确认旧主机连接器仍然关闭。
13. 打开新主机连接器。
14. 补拉停机时间窗的订单和售后。
15. 执行受控订单、库存、面单、发货和售后测试。

## 10. 验收

### 10.1 数据验收

- MySQL 数据库、表和行数一致；
- 订单金额汇总一致；
- 库存、预占和可售汇总一致；
- 履约和售后状态一致；
- Outbox 汇总一致；
- MinIO 对象数量和容量一致；
- 抽样 SHA-256 一致；
- Git 分支、标签、提交和未跟踪资料齐全。

### 10.2 功能验收

- 健康检查；
- 登录和权限；
- 订单查询；
- 库存查询；
- 附件读取；
- 异常工作台；
- 平台授权和回调；
- 订单补拉；
- 库存同步；
- 电子面单；
- 发货回传；
- 售后回写。

### 10.3 运维与安全验收

- 监控、日志和告警正常；
- 新备份任务正常；
- 证书和防火墙正常；
- Windows 服务和计划任务正常；
- 日志不包含密钥和完整隐私数据；
- 旧主机连接器保持关闭；
- 新主机是唯一生产写入主机。

## 11. 观察期

- 前 2 小时持续监控；
- 24 小时内重点核对订单漏单和重复、库存差异、消息积压、发货和售后失败；
- 72 小时后完成第一次正式迁移复盘；
- 旧主机至少保留 7 天，只读且禁止连接平台；
- 关键迁移备份建议至少保留 30 天；
- 观察稳定后轮换数据库、平台、MinIO 和 JWT 等关键密钥。

## 12. 回滚

### 12.1 回滚触发

- 数据库或对象校验不一致；
- 核心接口或登录不可用；
- 大量平台授权或回调失败；
- 漏单或重复订单；
- 负库存或重复发货；
- 无法解释的退款差异；
- 数据库、消息或磁盘持续异常，无法在停机窗口内修复；
- 敏感数据泄漏。

### 12.2 新主机尚未生产写入

1. 关闭新主机应用和连接器。
2. 恢复旧主机网络、应用和监控。
3. 确认新主机连接器仍关闭。
4. 开启旧主机连接器。
5. 补拉停机时间窗。
6. 验证业务恢复。

### 12.3 新主机已经生产写入

1. 关闭新主机全部写入和连接器。
2. 备份新主机最终状态。
3. 导出切换点后的订单、库存、履约、售后和 Outbox 增量。
4. 识别已执行的平台外部副作用。
5. 完成增量核对和受控回放。
6. 只有确认旧主机数据已追平后，才允许开启旧主机。

新主机产生生产写入后，优先采用前向修复。禁止直接启动旧主机造成数据回退、重复发货或重复库存同步。

## 13. 清理

只有业务负责人和技术负责人共同确认迁移稳定后，才可以：

- 删除迁移临时文件；
- 注销旧主机证书和密钥；
- 删除旧主机平台白名单；
- 停用旧主机计划任务；
- 删除旧主机容器和卷；
- 回收旧主机。

删除前再次确认备份可读取、保留期满足要求，并保存最终迁移报告。

## 14. 完成标准

迁移完成必须同时满足：

- 所有清单项目已迁移并验证；
- 所有 SHA-256 一致；
- 数据和业务基线一致；
- 核心功能和外部平台流程通过；
- 新主机是唯一生产主机；
- 监控、告警和备份正常；
- 72 小时观察无重大异常；
- 回滚资料仍在有效保留期内；
- 负责人完成书面验收。
