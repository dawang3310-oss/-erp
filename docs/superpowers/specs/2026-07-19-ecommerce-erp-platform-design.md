# 自用多平台电商 ERP 总体设计规格

- 文档日期：2026-07-19
- 文档状态：总体设计已确认，待用户审阅书面规格
- 建设周期：9–12 个月
- 研发团队：4–8 人
- 部署区域：中国大陆公有云

## 1. 项目背景

公司计划从零建设一套自用电商 ERP，统一管理微信视频号小店、天猫、淘宝、京东、拼多多、抖音、小红书、快手小店和得物，共 9 个国内平台。业务预计日均 1,000–10,000 单，大促峰值约 30,000 单。履约采用自营仓、第三方云仓和供应商一件代发并存的模式。

系统经营多种商品：普通实物商品、需要批次与效期管理的食品/美妆/保健品，以及需要序列号或唯一码追踪的 3C/奢侈品。供应链以采购成品和供应商代发为主，不包含生产制造。ERP 承担业务核算和经营分析，正式总账、税务及法定财务报表由金蝶或用友负责。

## 2. 建设目标

系统必须实现以下业务闭环：

1. 从各平台可靠获取订单、商品、售后和账单数据。
2. 将平台商品映射为统一内部 SKU，将平台订单转换为统一销售订单。
3. 在下单、取消、发货和退货全过程保持库存一致，避免重复扣减和超卖。
4. 根据库存、区域、时效和规则，将订单路由到自营仓、云仓或供应商代发。
5. 完成拣货、复核、打包、面单、出库和发货回传。
6. 完成退款、退货、换货、退件质检和库存回补。
7. 对平台回款、退款、佣金和履约费用进行核销，输出订单级利润。
8. 对快递账单、运单、仓库称重和合同价进行核对，识别重复计费、重量及价格差异。
9. 将审核后的业务汇总凭证传递给金蝶或用友。
10. 为所有关键操作提供权限控制、审计、监控、告警和灾难恢复能力。

## 3. 范围边界

### 3.1 本项目包含

- 多店铺、多平台授权和连接器管理
- 商品、SPU、SKU、条码、渠道商品映射和组合装
- 订单获取、审单、拆合单、分仓、缺货和异常处理
- 多仓库存、库位、批次、效期、FEFO、序列号和唯一码
- 采购订单、采购入库、采购退货和供应商结算
- 自营仓轻量 WMS
- 第三方云仓适配和库存/出库对账
- 供应商一件代发和供应商协同
- 电子面单、物流轨迹和平台发货回传
- 快递公司、月结账号、计价合同、快递账单和运费对账
- 仅退款、退货退款、换货及退件质检
- 平台账单、回款核销、费用拆分和订单利润
- 金蝶/用友财务接口
- 权限、审计、报表、任务、监控、告警和运维后台

### 3.2 本项目不包含

- 完整财务总账、税务申报、固定资产和法定财务报表
- BOM、MRP、自有生产和委外加工
- 面向外部商家的 SaaS 多租户计费体系
- 复杂 CRM、广告投放平台和全渠道客服聊天系统
- 首期智能补货、算法预测和自动定价

上述不包含项不得阻塞首期订单履约闭环。未来如需建设，应作为独立子项目设计。

## 4. 平台接入策略

平台按以下顺序接入：

1. 第一批：天猫/淘宝、京东、拼多多、抖音。
2. 第二批：微信视频号小店、小红书、快手小店。
3. 第三批：得物。

所有平台通过独立连接器接入。连接器负责 OAuth 或平台授权、签名、Token 刷新、限流、重试、消息订阅、定时补拉、原始报文归档和字段转换。ERP 核心不得包含平台专有字段或签名逻辑。

订单以平台推送为实时通道，以按更新时间窗口拉取为补偿通道。每次拉取窗口保留重叠时间，利用幂等键消除重复数据。平台订单幂等键采用“平台＋店铺＋平台主订单号”；售后幂等键采用“平台＋店铺＋平台售后单号”。

平台资质申请与研发并行启动。正式排期以应用审核、店铺授权、订单隐私解密、电子面单及相应类目权限实际开通为准。若某个平台权限未按期获得，可使用该平台认可的服务商接口临时过渡，但核心 ERP 数据模型和业务规则不得依赖该服务商。

平台能力参考：

- [京东开放平台 API 列表](https://help.jd.com/oapihelp/question-557.html)
- [拼多多开放平台商家自研应用入口](https://open.yangkeduo.com/application/)
- [小红书开放平台开发者角色](https://xiaohongshu.apifox.cn/doc-2811119)

## 5. 总体技术架构

### 5.1 架构风格

采用“模块化单体核心＋独立平台连接器＋消息队列”的架构。

- ERP 核心是一个模块化单体应用，内部按商品、订单、库存、采购、履约、仓储、售后、业财、权限和运营划分模块。
- 各平台连接器作为独立进程部署，可单独扩容、停机和升级。
- 模块之间通过公开应用服务、领域事件或只读查询接口协作，禁止跨模块直接修改数据表。
- 当前阶段不拆分大量微服务。订单量或团队规模显著增长后，可优先拆分平台连接器、订单导入和库存同步等明确瓶颈。

该架构避免早期分布式事务和运维负担，同时保留未来拆分边界。

### 5.2 参考技术栈

- 后端：Java 21、Spring Boot 3、模块化分层架构
- 管理端：Vue 3、TypeScript、Vite
- PDA：响应式 Web/PWA，使用设备相机或扫码枪
- 主数据库：MySQL 8 高可用版
- 缓存与短期幂等：Redis 高可用版
- 消息队列：RocketMQ 托管版
- 文件与报文：对象存储 OSS
- 可观测：OpenTelemetry、集中日志、指标和告警
- 部署：Docker 容器、阿里云托管 Kubernetes；同等能力的大陆公有云服务可以替换，不改变业务设计
- CI/CD：代码扫描、自动测试、镜像构建、灰度部署和一键回滚

### 5.3 数据一致性原则

- 核心交易在单一数据库事务内完成。
- 跨进程动作使用 Outbox 事务消息：业务数据和待发送事件同事务提交，再由后台发布到消息队列。
- 消费端通过业务幂等键和消费记录保证至少一次投递下的结果唯一。
- 外部 API 操作保存请求、响应、业务键、重试次数和最终状态。
- 外部调用采用指数退避重试；超过阈值进入死信/人工工作台，禁止无限重试。

## 6. 核心领域模型

### 6.1 商品

- SPU 保存品牌、类目和公共属性。
- 内部 SKU 是库存核算和履约的最小主体，保存规格、条码、计量单位以及批次、效期和序列号策略。
- 渠道商品映射保存平台、店铺、平台商品 ID、平台 SKU ID 与内部 SKU 的关系。
- 组合装、套装和赠品通过组件清单关联真实 SKU；销售组合商品时按组件数量锁定库存。
- 未映射到内部 SKU 的平台订单不得自动审单，必须进入异常工作台。

### 6.2 订单

系统同时保存两种订单：

- 平台原始订单：保存原始报文、平台状态、优惠、密文地址、接口版本和获取时间，不覆盖历史版本，用于审计和重放。
- ERP 销售订单：保存主单、明细、金额分摊、收货快照、履约单和售后关联，用于内部业务处理。

一个平台订单可以因不同仓库或履约方式拆成多个履约单。合单发货必须满足同平台、同店铺、同收货信息、平台允许合单以及仓储规则允许等条件。履约状态不得反向覆盖平台原始状态。

### 6.3 库存

库存维度为：货主、仓库、库位、内部 SKU、批次、库存状态；启用序列号的商品还必须逐件记录唯一码。

库存状态至少包含：

- 实物库存
- 可售库存
- 锁定库存
- 冻结库存
- 在途库存
- 残次库存

渠道可发布库存按以下原则计算：

`渠道可发布库存 = 可售库存 - 安全库存 - 已锁定但尚未同步的数量`

库存余额是不可变库存流水的汇总结果。采购入库、销售锁定、取消释放、销售出库、退货入库、盘点调整、调拨和冻结/解冻都必须产生带来源单据、原因和操作人的流水。业务模块禁止直接修改库存余额。

下单锁库存事务依次执行：订单幂等检查、SKU 映射、履约仓选择、带数量条件的库存更新、锁定流水写入、Outbox 事件写入。库存不足时订单进入“缺货待处理”，不得产生负库存。

## 7. 订单与履约流程

标准订单流程如下：

1. Webhook 接收平台推送，定时任务补拉遗漏订单。
2. 连接器保存原始报文并完成幂等检查。
3. 平台字段转换为统一订单模型。
4. 完成 SKU 映射、风控/人工审单规则和库存锁定。
5. 履约路由器根据店铺规则、库存、区域、仓库优先级、物流时效、成本和商品策略选择履约方式。
6. 生成一个或多个履约单，下发自营仓、云仓或供应商。
7. 获取面单并执行拣货、复核、打包、称重和出库，或等待外部履约方回传。
8. 将物流公司和单号回传平台。
9. 定时对账平台状态、履约状态、仓库出库和库存。

统一履约状态为：待分仓、已锁库存、已下发、作业中、已出库、已回传平台、已签收、已关闭。

重新选仓规则：未下发的履约单可直接重新路由；已下发未作业的履约单必须先确认取消成功；已经作业或出库的履约单禁止自动改派，以避免重复发货。

## 8. 仓储与代发

### 8.1 自营仓 WMS

首期轻量 WMS 包含：采购收货、质检、上架、库位、移库、盘点、补货、波次、拣货、复核、打包、称重、面单、出库和退货入库。

批次商品按 FEFO（最早失效优先）分配；序列号商品在拣货或复核环节逐件绑定。作业人员通过 PDA 扫描条码完成关键动作，系统必须校验 SKU、批次、库位和任务。

### 8.2 第三方云仓

云仓适配器负责出库单下发、取消、状态回传、物流回传、库存同步和差异对账。下发接口必须幂等。云仓库存差异生成差异单，由人工核查后通过库存调整单处理，不得直接覆盖 ERP 账面库存。

### 8.3 供应商一件代发

系统生成供应商代发单，可通过 API、供应商门户或固定模板下发。供应商确认接单、反馈缺货并回传物流。仅向被选择的供应商提供完成该履约所需的收货信息，并记录查看和导出审计。

## 9. 售后

统一售后单支持仅退款、退货退款、换货、部分退款和部分退货。

- 未出库：尝试拦截履约，成功后释放锁定库存。
- 作业中：向仓库发送拦截请求，确认结果后更新状态。
- 已出库：尝试物流拦截；失败则等待客户退货。
- 退货收货：质检后进入良品、残次品或待检库存。
- 退款：单独记录资金状态，不以退款成功推断退货已经入库。

平台售后、仓库退件和资金退款三者分别维护状态并通过业务关系关联。

## 10. 业财、快递对账与财务系统

### 10.1 平台账单与订单利润

ERP 保存订单收入、平台补贴、退款、商品成本、平台佣金、服务费、仓储费、物流费、代发费和其他分摊费用。

订单贡献毛利公式为：

`订单贡献毛利 = 实际收入 + 平台补贴 - 退款 - 商品成本 - 平台费用 - 履约费用 - 其他分摊费用`

平台账单通过 API 或文件获取，原始文件永久留存。标准化后按订单、售后单和平台结算单匹配。差异类型包括少结、多结、未结算、未知费用、退款未扣回、订单不存在和跨期结算。自动匹配项核销，差异项进入人工工作台。

### 10.2 快递费用对账

系统维护快递公司、月结账号、发货仓、服务产品、结算币种、合同价模板及其生效区间。合同价支持首重、续重、重量进位规则、始发地、目的地区间、偏远地区、超长超重、保价、代收、退回、转寄、拦截和其他附加费。计价规则必须版本化；历史运单始终使用发货时有效的规则版本重算，不能因新合同生效而改变历史预估费用。

快递对账使用以下数据源：

- ERP 履约单、包裹、面单和运单号
- 自营仓出库称重、尺寸和发货时间
- 快递公司 API 或 Excel/CSV 月结账单
- 合同计价规则、折扣和附加费规则
- 物流拦截、退回、转寄和异常件记录
- 云仓结算单中的物流费用

快递账单行的业务唯一键采用“快递公司＋月结账号＋账单批次＋运单号＋费用类型”。重复导入同一账单不得重复形成应付。标准对账流程如下：

1. 通过 API 或文件导入快递原始账单，保存原文件、文件摘要、账期和导入人。
2. 将各快递公司的字段和费用代码转换为统一账单明细。
3. 以快递公司、月结账号和运单号精确匹配 ERP 包裹；退回件、转寄件同时关联原运单。
4. 使用仓库实称重量、目的地和发货时合同版本计算预估运费。
5. 比较账单重量、计费重量、服务产品、区域、基础运费及各项附加费。
6. 在配置的金额和重量容差内自动核销，超差或无法匹配的明细进入快递差异工作台。
7. 财务或物流负责人审核差异、发起快递申诉、登记调账结果并形成快递应付结算单。
8. 结算完成后将实际运费回写包裹及订单利润，并生成财务凭证来源数据。

差异工作台至少识别：有单无运单、有运单无账单、账单无业务单、重复计费、实称与计费重量超差、目的地区间错误、合同单价错误、附加费异常、拦截/退回费用异常、服务产品不一致和跨账期补扣。

重量及金额容差按快递公司、服务产品和仓库配置。系统同时保留仓库实称、快递计费重量、差值、计价过程和合同版本，便于申诉举证。已确认结算的账期不得直接修改；后续补扣或返还通过下一账期的调整单处理。

第三方云仓代收的快递费优先通过云仓结算单核对，不再与自营月结账号重复确认应付。系统仍应以运单号检查云仓账单和快递公司账单是否重复收费。供应商代发的运费按供应商结算规则处理，只有使用公司快递月结账号时才进入快递公司对账。

### 10.3 财务系统接口

ERP 按日或结算周期生成凭证草稿，通过幂等批次号发送给金蝶或用友。财务人员审核后正式入账。每笔凭证可以下钻到 ERP 来源单据。已关账期间禁止直接修改业务金额，调整必须使用红冲或补差单。

## 11. 安全、隐私与审计

- 账号采用企业身份或统一认证，离职账号及时停用。
- 权限采用 RBAC，并叠加店铺、仓库、组织等数据范围。
- 收货人姓名、电话、地址等个人信息字段级加密，页面按岗位脱敏展示。
- 解密遵循履约目的和最小权限，批量导出需要审批并记录审计。
- 平台密钥和 Token 存入云 KMS/密钥管理服务，自动轮换，不得写入代码、配置仓库或普通日志。
- 改价、强制审单、库存调整、重新发货、关账、凭证重推和数据导出等操作必须记录操作人、时间、原因及前后值。
- 数据保留和删除策略遵循平台规则及适用的个人信息保护要求；业务侧不得为了报表长期复制明文个人信息。

## 12. 可观测、备份与容灾

监控至少覆盖：订单同步延迟和积压、平台 API 错误率和限流率、消息积压、库存同步差异、负库存拦截、云仓/代发失败、发货回传失败、平台账单未匹配金额、快递账单未匹配金额与重量超差、数据库和缓存健康度。

日志、指标和链路追踪统一携带请求 ID、平台订单号、ERP 订单号和履约单号。告警按严重程度路由到值班人员，并附带可执行的处置入口。

生产应用跨可用区部署。数据库使用高可用实例、时间点恢复和每日自动备份，并保存异地备份副本。容灾目标为 RPO 不超过 5 分钟、RTO 不超过 2 小时。每季度执行一次真实备份恢复演练并保留记录。

## 13. 测试策略

- 单元测试：状态机、金额分摊、库存计算、选仓和权限规则。
- 契约测试：每个平台的签名、请求、响应、错误码和字段兼容。
- 集成测试：MySQL、Redis、RocketMQ、对象存储和外部适配器。
- 端到端测试：普通下单、拆单、合单、赠品、取消、发货、仅退款、退货退款和换货。
- 性能测试：至少按预计峰值 2 倍进行接单、锁库存和发货回传压测。
- 故障测试：平台超时、重复推送、消息重复、消息延迟、云仓拒单、数据库主备切换和缓存不可用。
- 安全测试：越权、敏感数据泄漏、批量导出、密钥暴露和审计完整性。
- 快递对账测试：合同版本切换、重量进位、区域价、附加费、退回件、重复账单、跨期补扣和云仓重复计费。

每个平台建立脱敏黄金报文库，覆盖普通单、预售、赠品、改址、取消、部分退款、拆单等典型和边界场景。平台接口版本升级必须通过自动回归后才能发布。

## 14. 实施路线

### 第 1–2 月：基础与资质

- 完成平台开发者/自研商家入驻和权限申请。
- 建立代码仓库、CI/CD、云环境、权限和审计骨架。
- 完成商品、SKU、店铺、仓库、供应商主数据。
- 定义统一订单、库存、履约和售后契约。

### 第 3–4 月：核心交易与淘宝/天猫

- 完成订单中心、库存账本和 Outbox 事件机制。
- 完成淘宝/天猫连接器和商品映射。
- 完成自营仓入库、库位、拣货、复核、打包和出库基础功能。

### 第 5–6 月：京东、拼多多、抖音与一期试运行

- 完成京东、拼多多、抖音连接器；拼多多连接器覆盖商品映射、订单、售后、库存同步、物流及发货回传。
- 完成电子面单、云仓适配和平台发货回传。
- 完成包裹、仓库实称重量、快递产品和月结账号等快递对账基础数据采集。
- 选择少量店铺与 SKU 灰度运行，完成订单与库存对账。

### 第 7–9 月：第二批平台与供应链

- 接入微信视频号小店、小红书和快手小店。
- 完成采购、供应商代发、退货和售后中心。
- 完成批次效期、FEFO、序列号和唯一码作业。

### 第 10–12 月：得物、业财与全面切换

- 接入得物及其特殊履约规则。
- 完成平台账单、快递费用对账、订单利润、供应商结算和金蝶/用友接口。
- 完成峰值压测、故障演练、备份恢复和安全审计。
- 按店铺分批全面切换，保留平台后台人工应急流程。

## 15. 团队配置

建议最小稳定配置为：

- 1 名产品经理/业务分析师
- 1 名技术负责人
- 2–3 名后端工程师
- 1–2 名前端工程师
- 1 名测试/质量工程师

早期云运维可由技术负责人或后端兼任，但生产上线前必须明确值班和故障负责人。仓储、财务和平台运营部门各指定一名业务负责人，负责规则确认、测试数据和验收。

## 16. 上线验收标准

系统进入单个平台正式全量运行前，必须同时满足：

1. 连续 7 天订单同步无不可解释漏单，重复订单不会重复入账。
2. 重复推送、接口超时和消息重投不会重复扣库存或重复发货。
3. ERP 与自营仓/云仓库存差异可以定位到具体单据并闭环。
4. 发货、取消和售后状态与平台对账差异均有明确处理结果。
5. 权限、敏感字段脱敏、数据导出和关键操作审计通过验收。
6. 完成预计峰值 2 倍压测，关键接口无错误率突增或不可接受积压。
7. 完成数据库备份恢复和至少一次依赖故障演练。
8. 建立人工应急操作手册、平台后台兜底流程和值班联系人。
9. 至少完成一个快递结算周期的对账，账单行自动或人工匹配率不低于 99%，所有未匹配和超差明细均有责任人、原因和处理结果，且不存在重复确认应付。

## 17. 主要风险与缓解措施

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 平台应用审核或敏感权限延期 | 连接器无法按期联调 | 第 1 月启动申请；建立沙箱/黄金报文；必要时用认证服务商临时过渡 |
| 平台接口和状态规则变化 | 订单或售后处理异常 | 独立连接器、防腐层、契约测试、原始报文归档和版本兼容 |
| 多仓库存延迟导致超卖 | 缺货与消费者投诉 | ERP 作为库存真相源、安全库存、事务锁定、同步监控和人工熔断 |
| 云仓或供应商状态不可靠 | 重复发货或长时间未发货 | 幂等下发、状态对账、超时告警、改派前强制取消确认 |
| 多品类仓储规则复杂 | 作业错误和库存不准 | 按 SKU 启用批次/序列号策略，PDA 扫描校验，先小范围试仓 |
| 账单口径不一致 | 毛利失真 | 保留原始账单、规则版本化、差异工作台、财务月度抽查 |
| 快递合同价和附加费规则复杂 | 运费预估或应付错误 | 合同规则版本化、仓库实称留痕、容差配置、账单逐行对比和申诉闭环 |
| 4–8 人团队范围过大 | 交付延期 | 按平台分批、先完成闭环、限制首期范围、每两周检查关键路径 |

## 18. 设计决策总结

本项目选择自研核心 ERP、独立平台连接器和分批上线。模块化单体是现阶段的默认架构，MySQL 事务和 Outbox 负责核心一致性，RocketMQ 负责削峰和异步集成。ERP 是商品映射、销售订单、库存和业务核算的真相源；平台、仓库和财务系统通过可追溯适配器协作。首要交付目标是稳定完成从平台订单到发货、售后和对账的业务闭环，而不是在首期复制成熟商业 ERP 的全部功能。
