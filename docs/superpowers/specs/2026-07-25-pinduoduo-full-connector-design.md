# 拼多多完整连接器设计

## 1. 背景与决策

公司已有一个与开发者认证主体一致的拼多多店铺，但尚未注册和申请拼多多开放平台商家自研应用。本项目选择直接建设独立拼多多连接器，并同步办理开放平台资质。研发阶段使用黄金报文和本地平台模拟器，取得真实权限后替换模拟 API 客户端并执行同一套契约回归。

正式范围选择完整闭环：授权、订单、商品、SKU、库存、物流、发货、售后和电子面单。内部按模块独立开发和验收，但生产环境采用统一总开关，一次性开放全部能力。

拼多多官方开放平台把商家自研系统定位为可接入商品、交易和物流等能力的商家后台系统。申请流程为注册账号、开发者认证、创建应用或服务；详细权限和接口文档以登录后的控制台为准：

- [拼多多开放平台](https://open.yangkeduo.com/)
- [商家自研应用入口](https://open.yangkeduo.com/application/home)

## 2. 目标

- 在不污染 ERP 核心模型的前提下，实现单店铺拼多多完整业务闭环。
- 平台订单可追溯、可补拉、可幂等导入 ERP，并进入现有库存和履约流程。
- ERP 作为内部 SKU、库存和业务核算的真相源。
- 商品、库存、发货、售后和面单操作具有明确的外部副作用边界，失败后可安全重试。
- 在尚未取得平台凭证时完成除真实联调以外的代码、测试和运维准备。
- 为未来增加拼多多店铺保留 `shopId` 隔离，不以单店铺假设污染数据模型。

## 3. 非目标

- 不把拼多多字段、签名、Token 或错误码加入 ERP 核心模块。
- 不在本项目中接入淘宝、天猫、京东、抖音或其他平台。
- 不建设面向第三方商家的 SaaS、计费或服务市场能力。
- 不在未取得正式权限和真实店铺联调结果时打开生产总开关。
- 不允许平台库存反向覆盖 ERP 库存。
- 不自动审批存在财务或实物风险的售后申请。

## 4. 总体架构

`pinduoduo-connector` 作为独立 Java 21 / Spring Boot 进程部署。它依赖稳定的 `erp-connector-contracts`，通过标准订单、售后、商品和出站命令与 ERP 协作。ERP 核心不依赖连接器实现。

连接器采用端口与适配器结构：

- 入站适配器：定时任务、平台消息回调、管理命令。
- 应用服务：授权、拉取批次、转换、库存同步、发货、售后和面单用例。
- 出站适配器：拼多多 API、ERP 端口、MySQL、对象存储、消息队列和密钥系统。
- 模拟适配器：本地平台模拟器与黄金报文。

生产总开关位于连接器入口层。总开关关闭时可以执行健康检查、凭证验证、只读探测和模拟验证，但不得拉取生产业务数据或执行库存、发货、售后、面单等平台副作用。

## 5. 组件边界

### 5.1 授权中心

负责店铺授权状态、授权范围、Token 到期时间、刷新和吊销。`client_secret` 与 Token 只从密钥系统读取或以信封加密形式保存，禁止明文写入数据库、日志和告警。

授权记录以 `platform + shopId` 唯一。当前只有一个店铺，但授权、限流、游标、任务和审计记录都必须携带 `shopId`。

### 5.2 平台网关

统一完成参数规范化、签名、时间戳、请求 ID、序列化、限流、超时、重试和平台错误分类。业务模块不得自行拼接签名或直接调用 HTTP。

网关把响应划分为：

- 成功；
- 可重试：网络错误、超时、平台限流、临时服务端错误；
- 需要刷新授权：Token 过期或可恢复授权错误；
- 永久失败：权限不足、签名错误、参数非法、能力未开通；
- 状态冲突：平台已完成、已取消或不允许当前动作。

真实 API 方法、参数和错误码在取得控制台权限后加入版本化 API 目录；应用层只依赖稳定的领域请求和响应。

### 5.3 拉取调度器

订单、商品和售后分别使用独立调度器、限流器、工作队列及游标。单个能力拥堵不得阻塞其他能力。

游标保存：

- `platform`；
- `shopId`；
- 能力类型；
- 查询开始和结束时间；
- 页码或平台游标；
- 批次 ID；
- 最后成功时间；
- 状态与失败原因。

只有当前批次的全部页面完成原始归档、转换和 ERP 提交后，才提交新游标。恢复时从最后已确认批次开始，并使用重叠时间窗补拉。

### 5.4 消息接收器

平台消息用于缩短订单和售后的发现延迟，不作为唯一事实来源。消息验签、去重并归档后，只触发相应业务主键或时间窗的查询。定时补拉始终启用，用于处理消息丢失、乱序和重复。

### 5.5 防腐转换层

把拼多多模型转换为 ERP 标准模型，负责：

- 平台状态映射；
- 金额单位和精度；
- 时间和时区；
- 收件信息加密；
- 商品与规格标识；
- 物流公司标识；
- 售后类型与状态；
- 未知枚举保留和告警。

未知状态不得静默映射为正常状态。未知状态原文进入脱敏诊断记录，对应业务进入人工异常队列。

### 5.6 原始报文仓库

每次平台查询和回调都保存：

- 平台、店铺、业务类型和业务主键；
- 请求 ID 与批次 ID；
- 获取时间；
- 对象存储地址；
- 内容 SHA-256；
- 报文版本；
- 脱敏摘要。

原始正文只进入受控对象存储，不写应用日志。相同业务主键允许保存多个版本；相同内容摘要重复到达时不得重复创建业务单。

### 5.7 出站同步器

库存、发货、物流和面单分别使用独立 Outbox 消费器。出站命令必须有稳定业务幂等键、期望平台状态和最近一次平台结果。

请求超时后先查询平台状态，再决定确认成功、重试或进入人工异常；禁止在结果未知时直接重复执行有副作用的请求。

### 5.8 平台模拟器

模拟器提供与平台网关相同的领域接口，覆盖：

- 正常分页与增量数据；
- Token 过期和刷新；
- 限流与服务端错误；
- 网络超时和结果未知；
- 重复页、重复消息和乱序消息；
- 未知枚举和缺失字段；
- 部分批次成功；
- 库存与发货状态冲突；
- 售后和面单完整生命周期。

模拟器不声称替代真实联调。正式上线仍要求在已授权测试店铺执行真实 API 契约回归。

## 6. 业务数据流

### 6.1 授权和初始化

1. 管理员完成商家自研应用和店铺授权。
2. 连接器验证授权范围并读取店铺身份。
3. 创建订单、商品和售后游标。
4. 执行商品全量基线同步。
5. 校验物流、面单和库存权限。
6. 所有能力通过后，连接器进入“已就绪、未上线”状态。

### 6.2 订单接入

1. 消息或定时任务创建拉取批次。
2. 平台网关按重叠时间窗分页查询。
3. 每页响应先归档，再解析。
4. 使用 `platform + shopId + platformOrderId + updateVersion/contentHash` 幂等。
5. 转换为 `NormalizedOrder` 并调用 `OrderIngestionPort`。
6. ERP 完成 SKU 解析、库存预占、履约创建和 Outbox 写入。
7. 整批成功后提交游标；部分失败时不推进。

订单取消或售后通知不得直接删除 ERP 订单，必须转换为状态变更或售后流程。

### 6.3 商品和 SKU

首次授权后执行商品全量同步，之后按更新时间增量同步。渠道商品、规格、上下架状态和平台 SKU 保存在渠道主数据中。

平台 SKU 必须映射到内部 SKU。未映射 SKU 创建 `SKU_NOT_MAPPED` 异常，订单不能自动预占未知库存。运营人员建立映射后，可以幂等重放订单转换。

### 6.4 库存同步与对账

ERP 库存是唯一真相源。库存变化通过 Outbox 进入连接器，按 `shopId + platformSkuId` 合并，只保留尚未发送的最新绝对库存值。

库存同步必须：

- 遵守平台限流；
- 避免发送过期中间值；
- 保存平台确认结果；
- 定时读取平台库存进行差异对账；
- 差异超过配置阈值时告警并进入人工处理。

平台库存读取只用于对账，不反向覆盖 ERP 库存。

### 6.5 履约、物流与发货

ERP 完成拣货和复核后生成发货命令。连接器把内部物流公司映射为平台物流代码，提交运单号和发货信息。

发货幂等键由 `shopId + platformOrderId + fulfillmentId` 组成。若超时，必须先查询平台订单或物流状态。平台已发货时确认本地命令完成；平台状态冲突时进入人工异常，禁止创建第二次履约。

### 6.6 售后

连接器覆盖平台取消、仅退款、退货退款和换货相关状态，并转换为统一售后事件：

- 未发货取消或退款：冻结履约并等待平台最终结果；
- 已发货仅退款：创建售后单并进入审核策略；
- 退货退款：记录退货物流，等待仓库收货和质检；
- 换货：拆分为退回和新履约过程；
- 平台最终退款：更新售后结果并产生核算事件。

ERP 不自动同意超出明确规则的售后申请。退款金额和平台最终状态以平台结果为准，ERP 保存过程和核算数据。

### 6.7 电子面单

连接器同步面单账户、网点和模板能力。仓库请求面单时：

1. 校验履约、地址、物流服务和授权。
2. 以履约 ID 创建幂等申请。
3. 保存平台面单号和加密打印数据。
4. 把打印任务交给仓库。
5. 换单或取消时保留原记录并建立新旧关联。

面单数据遵循收件隐私访问控制，不允许进入通用日志、指标标签或错误正文。

## 7. 一致性与恢复

- 入站以平台业务主键和内容版本幂等。
- 出站以稳定业务命令 ID 幂等。
- MySQL 事务只覆盖连接器本地状态和 Outbox，不跨平台 API。
- 外部副作用使用“本地命令 → 平台调用 → 状态查询确认 → 本地完成”的状态机。
- 超过重试上限的命令进入死信表，不直接修改业务表。
- 死信记录错误分类、脱敏上下文、平台请求 ID 和建议动作。
- 人工重放复用原业务幂等键并记录操作者。
- 平台恢复后按游标重叠补拉，并按 Outbox 顺序补偿出站命令。

## 8. 安全与审计

- 密钥、Token、收件信息和面单数据加密存储。
- 生产凭证只从环境变量或密钥系统注入。
- 日志禁止出现 `client_secret`、Token、完整手机号、地址和原始报文正文。
- 权限按订单、商品、库存、物流、售后、消息和电子面单的最小范围申请。
- 所有管理操作需要 ERP 管理员身份和权限。
- 授权变化、库存回写、发货、面单申请或取消、售后状态变化均写审计日志。
- 审计记录包含操作者、店铺、业务主键、请求 ID、响应摘要和时间，不包含敏感正文。
- 非授权店铺数据在入口层拒绝。

## 9. 可观测性与告警

至少暴露以下指标：

- 订单拉取延迟与最后成功时间；
- 各能力游标停滞时间；
- API 请求成功率和延迟；
- 限流次数和退避时间；
- Token 刷新失败；
- 原始报文归档失败；
- 转换失败和未知状态；
- SKU 未映射数量；
- 库存同步积压和库存差异；
- 发货回传失败；
- 售后积压；
- 面单申请、取消和失败数量；
- 死信数量和最老死信年龄。

指标标签只允许平台、店铺内部 ID、能力、结果分类和错误分类，不允许平台订单号、手机号、地址或 Token。

## 10. 测试策略

### 10.1 单元测试

覆盖签名、参数排序、时间戳、金额精度、错误分类、状态转换、字段映射、幂等键和隐私脱敏。

### 10.2 黄金报文契约测试

订单、商品、库存、物流、退款、退货退款、换货和电子面单分别包含正常、缺字段、重复、未知状态和版本变化样例。取得真实测试响应后，脱敏加入版本化契约基线。

### 10.3 模拟器集成测试

覆盖 Token 失效、限流、超时、分页重复、消息乱序、部分批次失败、平台状态冲突和恢复补偿。

### 10.4 MySQL 集成测试

覆盖游标事务、原始报文追加、入站和出站幂等、任务抢占、Outbox、死信以及并发恢复。

### 10.5 端到端测试

完整路径为：平台下单 → ERP 入单 → SKU 映射 → 库存预占 → 面单 → 发货回传 → 售后退款。

### 10.6 安全与容量测试

验证密钥不明文保存、日志不含隐私、错误响应不泄漏 Token、跨店铺访问被拒绝。容量测试按日均 1,000–10,000 单和大促峰值约 30,000 单执行，并验证平台限流条件下积压可恢复。

## 11. 平台资质工作流

业务负责人和研发负责人同步完成：

1. 注册拼多多开放平台账号。
2. 完成与现有店铺同主体的开发者认证。
3. 创建商家自研应用。
4. 申请交易、商品、库存、物流、售后、消息和电子面单权限。
5. 授权现有店铺。
6. 安全地交付测试凭证。
7. 导出或记录登录后可见的正式 API 目录、权限说明、限流规则、错误码和测试响应。
8. 对模拟器契约与真实平台进行差异复核。

权限审核可以与研发并行，但未完成真实联调前不得生产上线。

## 12. 实施分解

完整范围拆为四个可独立测试和评审的实施计划，但不单独生产上线：

1. 平台基础与订单：授权、平台网关、模拟器、原始报文、消息、游标和订单入站。
2. 商品与库存：商品基线、增量同步、SKU 映射、库存出站和差异对账。
3. 履约与面单：物流映射、电子面单、发货回传和结果未知恢复。
4. 售后与统一投产：取消、退款、退货退款、换货、容量验证、运维演练和生产总开关。

四个计划共享本设计中的数据、安全和幂等约束。前三个计划完成后生产总开关仍保持关闭；只有第四个计划通过统一上线门后，才一次性开启全部生产能力。

## 13. 统一上线门

生产总开关只能在以下条件全部满足后开启：

- 所需平台权限全部审核通过；
- 真实测试店铺完成全部能力联调；
- 连续 7 天订单无漏单且无重复业务单；
- 商品和 SKU 映射流程可运营；
- 库存差异可检测和处理；
- 发货、售后和面单失败可追踪、重试或人工处理；
- 密钥轮换、备份恢复、故障和回滚演练完成；
- 单元、契约、模拟器、集成、端到端、安全和容量测试全部通过；
- 运营人员完成订单异常、库存差异、发货失败和售后处理培训。

出现漏单、跨店铺数据、负库存、重复发货、无法解释的退款差异或敏感数据泄漏时，立即关闭生产总开关，并恢复平台后台人工操作。

## 14. 验收结果

本设计完成的标志是：

- 单店铺完整闭环能力均有可执行实现和自动化测试；
- 模拟器与真实平台使用同一领域端口；
- 平台专有逻辑不进入 ERP 核心；
- 连接器能够从崩溃、重复消息、限流和结果未知中安全恢复；
- 所有外部副作用可审计；
- 未取得权限时可以完成模拟验收，但生产总开关保持关闭；
- 取得权限后通过真实店铺契约回归和统一上线门。
